# 2.1 Choose Your Own Adventure

▶ [Watch in the video (38:51)](https://www.youtube.com/watch?v=7x6C8_FXEK0&t=2331s)

Branches let you experiment and maintain multiple parallel project histories without
committing to one. That makes trying out new changes less risky: they don't interfere with
the main, reliable version of the code, which you can always switch back to. It's akin to
writing drafts.

Often there's an array of things to get done at once (tests, code formatting,
documentation). With branches you can work on them in parallel, in whatever order makes
sense, or hand each one to a different team member. Here the project gets two parallel
branches: one adds linting, the other adds testing.

**Starting point:** the `git-tutorial` clone from [1.15](../01-overview/15-this-is-how-you-collaborate.md).
You'll also need Python 3.

## Adventure 1: linting

**Linting** means checking code against a style guide. For a language like Python there
are regimented rules for things like whitespace and syntax, and a tool can check (and
often fix) your code against them. This example uses [Ruff](https://docs.astral.sh/ruff/),
a popular linter for Python.

```bash
git checkout main
git checkout -b linting

echo "ruff" > requirements.txt
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

The virtual environment shouldn't be part of the repository. A **`.gitignore`** file lists
paths Git should ignore: here the virtual environment, Python's generated bytecode files,
and the backup files some editors (like Emacs) leave behind:

```bash
cat > .gitignore <<'EOF'
venv
__pycache__
*.pyc
*~
EOF
git status  # venv/ doesn't appear
```

To have some Python code to lint, check out `script.py` from the `python-script` branch.
`git checkout <branch> -- <file>` brings a single file over from another branch:

```bash
git checkout python-script -- script.py
ruff check  # "All checks passed!"
git add . && git commit -m "Add linting to the project"
```

## Adventure 2: testing

Back on `main`, start a second, parallel branch. Since it branches from `main` rather than
`linting`, it doesn't have the `.gitignore` yet, so that gets created again:

```bash
git checkout main
git checkout -b testing

mkdir tests
cat > tests/test_project.py <<'EOF'
def test_project():
    assert True
EOF

cat > .gitignore <<'EOF'
venv
__pycache__
*.pyc
*~
EOF

echo "pytest" > requirements.txt
pip install -r requirements.txt
pytest  # 1 passed
git add . && git commit -m "Add testing to project"
```

[pytest](https://docs.pytest.org/) is a popular testing framework for Python.

## Two adventures, side by side

```bash
git log --oneline --graph --all
```

```
$ git log --oneline --graph --all
* 3368bba Add testing to project
| * 1fb8b76 Add linting to the project
|/
| * d051e21 Update greeting in Python script
| * 09a1c62 Add Python script
|/
* 33aeb78 Add description to README
* 70aae54 Initialize project README
```

Linting and testing were added independently, and either could have come first. If two
people were doing this work at the same time, this is the point where they'd need to start
coordinating. That's the subject of the next module.
